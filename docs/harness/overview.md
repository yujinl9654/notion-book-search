# Harness Overview

## 목적

이 저장소는 구현 작업을 명시적인 동작과 회귀 방지 기준 위에 올려두기 위해 하네스 엔지니어링을 사용합니다.

이 프로젝트에서 하네스는 다음을 뜻합니다.

- 계속 지켜져야 하는 동작을 먼저 적어두는 것
- 사용자에게 보이는 상태와 결과를 구체적으로 정의하는 것
- 미래 테스트로 옮기기 쉽게 작은 케이스로 나누는 것
- 코드 변경 전후의 피드백 루프 일부를 문서로 관리하는 것

## 이 문서가 필요한 이유

OpenAI의 하네스 엔지니어링 글은 에이전트 친화적인 저장소가 잘 작동하려면 아래 조건이 중요하다고 설명합니다.

- `AGENTS.md`는 짧은 맵이어야 함
- 자세한 지식은 구조화된 문서에 있어야 함
- 검증 루프가 저장소 안에 인코딩되어 있어야 함
- 일관성 규칙을 초기에 적어두어야 드리프트가 덜 퍼짐

이 저장소는 그 구조를 처음부터 채택합니다.

## 읽는 순서

1. `AGENTS.md`
2. `docs/project-guide.md`
3. 해당 기능의 `docs/product-specs/` 문서
4. 해당 기능의 `docs/harness/` 문서
5. 구현 시작 시 해당 `docs/exec-plans/active/` 문서

## 문서 역할

### Feature 문서

Feature 문서는 아래를 설명합니다.

- 화면이나 흐름이 사용자에게 무엇을 제공하는지
- 누구를 위한 기능인지
- 어떤 상태와 흐름을 지원해야 하는지
- 수용 조건이 무엇인지
- 무엇이 현재 범위 밖인지

### Harness 문서

Harness 문서는 아래를 설명합니다.

- 무엇이 회귀하면 안 되는지
- 각 동작이 어떤 조건에서 발생하는지
- 기대 결과가 무엇인지
- 금지 결과가 무엇인지
- 미래 자동화에 가장 적합한 테스트 레벨이 무엇인지

## 케이스 템플릿

저장소에 더 엄격한 로컬 형식이 생기기 전까지는 아래 템플릿을 사용합니다.

```md
## [CASE-ID] Case Name

- Priority:
- Purpose:
- Conditions:
- Input / Action:
- Expected Result:
- Prohibited Result:
- Test Candidate:
```

## 테스트 후보 레벨

- `unit`: 순수 변환, 파싱, 정규화, 검증
- `integration`: 컴포넌트, 비동기 상태, 데이터 fetching, 상호작용 흐름
- `e2e`: 브라우저 수준의 사용자 여정

`Test Candidate`는 미래 자동화에 가장 적합한 대상을 뜻합니다. 테스트가 이미 존재한다는 뜻은 아닙니다.

## 갱신 규칙

- 사용자에게 보이는 동작이 바뀌면 해당 harness 문서를 함께 갱신합니다.
- 사용자에게 보이는 기능이 추가되거나 바뀌면 같은 변경 안에 자동화 테스트를 함께 추가하거나 갱신합니다.
- 테스트를 바로 작성하지 못하는 경우에는 이유와 남은 테스트 후보를 해당 harness 문서에 명시합니다.
- `정상 동작한다` 같은 모호한 표현은 피합니다.
- 가능하면 하나의 케이스는 하나의 보장에 집중합니다.
- 분기가 많은 동작은 긴 문단보다 작은 케이스 여러 개로 나눕니다.
- 구현 과정에서 반복되는 규칙이 드러나면, 패턴이 퍼지기 전에 이 문서나 전용 harness 문서에 기록합니다.

## 테스트 운영 규칙

- 기본 자동화 명령은 `pnpm test`입니다.
- React 컴포넌트 상호작용은 Vitest + Testing Library + jsdom으로 검증합니다.
- debounce, 지연 응답, 재시도 같은 시간 기반 동작은 fake timer로 시간을 명시적으로 제어합니다.
- 새 기능 테스트는 harness 케이스 ID와 연결될 수 있을 만큼 작고 구체적인 단위로 작성합니다.
- 품질 게이트는 `pnpm lint`, `pnpm test`, `pnpm typecheck`, `pnpm build`를 함께 통과하는 것을 기준으로 합니다.
